# 物业基础管理前端引用文档

## 1. 模块关系

`property-base-ui` 统一维护组织、用户、空间、客户、字典页面。收费、巡更等模块只管理自身业务菜单，不复制或导入公共 `baseMenu.json`。

```text
runtime-ui（JetLinks 宿主）
├─ property-base-ui          物业基础管理：一份菜单、五个页面
├─ charging-management-ui    收费业务
├─ cloud-patrol-ui           巡更业务
└─ 其他业务模块
```

本次只拆分前端，不新增后端服务或迁移数据库。请求沿用宿主 `@jetlinks-web/core` 请求实例，复用 SaaS 登录、租户和应用上下文，基础数据仍由现有物业基础后端维护。加载组件不等于获得权限，服务端接口与资产权限继续生效。

## 2. 配置 Git 子模块

公共模块目录为 `runtime-ui/modules/property-base-ui`，与收费、巡更平级。独立仓库为 `git@github.com:jetlinks-v2/property-base-ui.git`，维护分支为 `2.20`。

在 `runtime-ui` 登记子模块：

```powershell
$PropertyBaseRepoUrl = 'git@github.com:jetlinks-v2/property-base-ui.git'
git submodule add -b 2.20 $PropertyBaseRepoUrl modules/property-base-ui
```

主仓库只提交 `.gitmodules` 和子模块指针，公共源码和文档提交到公共仓库。其他开发者之后执行：

```powershell
git submodule update --init modules/property-base-ui
```

宿主已有 workspace 配置 `modules/**`，不需要另加目录。使用 Node.js 22.18 或更高版本；依赖统一在 `runtime-ui` 安装，不为业务模块再安装独立的 Vue。

## 3. 开发与构建

以下命令均在 `runtime-ui` 执行：

```powershell
# 单独调试公共模块，同时加载认证模块。
pnpm --filter property-base-ui dev
# 收费已接入公共模块，可直接使用原开发入口。
pnpm --filter charging-management-ui dev
# 其他业务应用联合调试，例如巡更。
pnpm --filter jetlinks-web-core dev -- -- --module-name cloud-patrol-ui,property-base-ui,authentication-manager-ui
```

其他业务模块只需在现有开发脚本的白名单加上 `property-base-ui`。不传白名单时宿主扫描全部模块；传了白名单就必须包含公共模块。仓库在磁盘上不代表会被构建加载。

### 独立发布

```powershell
pnpm --filter property-base-ui build
pnpm --filter charging-management-ui build
```

分别输出 `modules/property-base-ui/dist` 和 `modules/charging-management-ui/dist`。公共产物包含五个页面、远程资源入口和自己的 `baseMenu.json`，收费产物只保留收费模块内容。

通过 SaaS 动态前端应用分发时，公共产物需要作为独立前端应用配置到 SaaS，应用 ID 为 `property-base`，对应资源模块 ID 为 `property-base-ui`。前端应用记录、访问地址、静态资源发布按实际环境配置；启动基础后端不会自动发布前端。宿主按照发现的公共应用地址读取 `baseMenu.json`，并加载该应用页面。

### 聚合部署

```powershell
pnpm --filter charging-management-ui build:with-base
# 其他业务应用使用相同方式。
pnpm --filter jetlinks-web-core build -- -- --module-name cloud-patrol-ui,property-base-ui
```

当前 JetLinks 配置在白名单有多个模块时使用宿主模式，输出 `runtime-ui/dist`。它不是某个模块的独立远程包，不要混淆部署目录。网关地址仍在宿主环境配置中维护。

## 4. 菜单与按钮权限

公共模块提供唯一菜单树：物业基础管理 → 组织配置、用户管理、空间管理、客户管理、字典配置。

宿主自动扫描已加载模块的 `baseMenu.ts`，统一交给原有系统初始化界面。其他业务模块不导入、不拼接这份菜单。

首次拆分部署后，执行一次菜单初始化更新，使名称变为“物业基础管理”，并刷新保存的菜单选项。代码更新不会直接修改数据库里已初始化的名称和 `options.appName`；更新后刷新菜单缓存或重新登录。

本次保留原菜单 ID、code、URL 和按钮 ID：

| 页面 | 菜单 code | 地址 |
| --- | --- | --- |
| 物业基础管理 | `charging/basic` | `/charging/basic` |
| 组织配置 | `charging/OrganizationType` | `/charging/basic/organizations` |
| 用户管理 | `charging/User` | `/charging/basic/users` |
| 空间管理 | `charging/Space` | `/charging/basic/spaces` |
| 客户管理 | `charging/Customer` | `/charging/basic/customers` |
| 字典配置 | `charging/Dictionary` | `/charging/basic/dictionaries` |

已有 `charging/Space:save` 等按钮授权继续有效，后端 `property-*` 权限保持不变。`charging` 是公共菜单沿用的历史编码，不需要给每个业务模块生成不同前缀或权限副本。

五个基础页面均声明 `accessSupport.value: support`、`supportDataAccess: true` 及原资产类型，供授权界面生成数据权限选项。旧菜单只有 `assetType` 而缺少该声明时，页面可以打开但数据权限候选为空；已有环境需增量补齐菜单声明，并核对模板及角色的数据范围。支持数据权限不代表自动授予数据，人员读取仍由 `user` 资产权限控制；人员目录的组织范围与巡更执行资格分别配置。

本地聚合菜单不绑定收费应用 `appName`，由公共源码路由承载。独立 SaaS 前端分发时，宿主按实际公共应用记录补充 `appName`。

若其他业务模块以前复制过系统管理，例如 `handover/basic`，迁移时移除该模块的基础菜单和页面副本，并把原角色需要的权限授权到公共菜单。不同编码的旧菜单不会因初始化公共菜单而自动消失，须在对应应用迁移时处理。本次收费已完成迁移，其他独立业务仓库按本节接入。

## 5. 引用公共接口

运行时通过 JetLinks 注册中心获取公共能力；不要引用收费模块或公共模块内部的 `views/`、`hooks/`。

```ts
import { moduleRegistry } from '@jetlinks-web-core/utils/module-registry'
import type { PropertyBaseApis } from '@property-base-ui/public-api'

const getOrganizationTree = moduleRegistry.getResourceItem<PropertyBaseApis['getOrganizationTree']>(
  'property-base-ui', 'apis', 'getOrganizationTree',
)
if (!getOrganizationTree) throw new Error('物业基础管理模块未加载')

// 在调用方 hook/service 中执行，组件只负责展示。
const response = await getOrganizationTree()
if (!response.success) throw new Error(response.message)
const organizations = response.result
```

获取资源应放在宿主注册模块之后的 setup/hook/事件流程中，不在文件顶层缓存未注册资源。缺少模块时明确提示或阻止入口，不伪造空数据。正式业务页面的提示文案走该应用现有国际化。

实际公开能力包括：

| 能力 | 资源名称 |
| --- | --- |
| 组织树与详情 | `getOrganizationTree`、`getOrganization` |
| 同步用户查询 | `queryPropertyUsers`、`getPropertyUser` |
| 项目选项 | `getProjectOptions` |
| 项目空间树 | `getSpaceTree` |
| 字典选项 | `getDictionaryItems` |
| 客户查询 | `queryCustomers`、`getCustomer` |

参数和返回值以 `public-api.ts` 导出的 TypeScript 类型为准。部分接口返回宿主响应对象，部分已经经 `checked` 解包，不要重复解包。通过注册中心调用管理操作仍须相应按钮和后端权限。

需要引用公共类型或静态入口时，在业务模块 `tsconfig.json` 的 `compilerOptions.paths` 中保留原配置并增加：

```json
{
  "@property-base-ui/*": ["../property-base-ui/*"]
}
```

该路径适用于业务模块 `baseUrl` 为自身目录的现有配置。Vite 宿主已按 package name 注册模块别名，无需改 core。使用静态引用也要把公共模块加入开发和构建白名单。

## 6. 引用公共组件

目前实际提供：

| 名称 | 参数 | 说明 |
| --- | --- | --- |
| `ProjectSelect` | `value`、`treeData` | 完整组织树、仅项目可选；支持 `v-model:value` 和 `change` |
| `SpaceInformation` | `space` | 按空间类型逐项展示空间层级信息 |
| `UserIdentityTags` | `identities` | 展示服务端返回的身份名称与标签 |

例如项目选择（请求与转换仍放到业务 hook 中）：

```ts
import { ref } from 'vue'
import { moduleRegistry } from '@jetlinks-web-core/utils/module-registry'
import { toProjectTree, type ProjectTreeNode, type PropertyBaseComponents } from '@property-base-ui/public-api'

const projectId = ref<string>()
const projectTree = ref<ProjectTreeNode[]>([])
const ProjectSelect = moduleRegistry.getResourceItem<PropertyBaseComponents['ProjectSelect']>(
  'property-base-ui', 'components', 'ProjectSelect',
)
// 按上一节获取并检查组织响应后：
// projectTree.value = toProjectTree(organizations)
```

```vue
<ProjectSelect
  v-if="ProjectSelect"
  v-model:value="projectId"
  :tree-data="projectTree"
/>
```

项目选择是纯展示组件，不自行请求或同步。`toProjectTree` 保留完整组织层级，只让项目可选，非项目父组织禁用但仍可展开；下拉宽度随内容展开。调用方处理已有 loading/error/empty 状态，后端校验项目权限。

同一源码构建也可从 `@property-base-ui/public-api` 静态导入这些组件。不要导入模块 `index.ts`，它是 Vite 装配入口；不要跨模块深引用内部文件。

## 7. 验证与排错

1. 启动/构建白名单含公共模块，请求经过正确网关。
2. 初始化后仅一份物业基础管理，五个页面可以打开。
3. 原角色查询与按钮授权有效，无授权不能维护数据。
4. 项目树只允许项目选中，切换后空间和客户范围正确。
5. 引用后运行公共测试、业务测试及相应构建。

菜单缺失：检查公共模块是否被排除、是否初始化。菜单存在但打不开：检查发布地址及保存的 `appName`。资源为 undefined：检查注册时机、模块 ID 和资源名称。旧副本菜单仍在：对应业务应用尚未迁移。

公共模块更新后，各部署更新 Git 子模块指针并重新构建、发布；源码变更不会自动更新已经部署的页面。

## 8. 项目章

组织架构在关联空间下方展示项目章，仅项目类型显示。上传一张不超过 2MB、4096×4096 像素的 PNG/JPG 后自动保存，图片可点击放大，也可替换或确认移除。非项目隐藏；项目即使未关联空间也能维护。

既有按钮权限 `charging/OrganizationType:seal` 对应后端 `property-organization:seal`，修改类型的 `save` 权限不代替此权限。上传改走基础服务的受控 multipart 接口，由基础服务复用现有公共文件命令，校验真实图片并保存项目引用。基础服务需配置 `property.files.server-id`；不需要修改 SaaS 平台代码或数据，不能通过全量初始化菜单、改订阅或扩大权限绕过维护权限。

公开组织 API 返回 `projectSealFileId`；本模块组织架构使用 `uploadProjectSeal(id, version, file)` 一次完成上传保存，移除使用 `removeProjectSeal(id, version)`。两者返回最新组织详情，沿用宿主应用和认证上下文；冲突或网络结果不确定时刷新详情，禁止自动覆盖重试。装修等业务只通过基础服务 `GetPropertyProjectSealCommand` 读取当前有权项目章，不另外设置上传入口，也无需获得组织维护权限。

替换和删除只修改引用，SaaS 同步不覆盖。业务单据若使用项目章，应自行保存出具时的文件引用，避免随项目配置变化。
